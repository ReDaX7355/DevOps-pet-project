# DevOps Pet Project — Full-Stack инфраструктура с CI/CD и мониторингом

### Описание проекта
Проект создан как практическая DevOps-лаборатория для отработки инфраструктурных навыков, приближённых к production-среде.
Он предназначен для демонстрации навыков, полученных путем изучения методологии DevOps в системном администрировании, и показывает полный DevOps-пайплайн для небольшого веб-приложения:

- контейнеризация веб-приложения (frontend и backend)
- оркестрация через Docker Compose, Kubernetes
- CI/CD через GitHub Actions
- reverse proxy (Nginx)
- система мониторинга и логирования
- разделение окружений (dev / prod)
- создание облачной инфраструктуры (Terraform)
- настройка окружения и деплой на серверах (Ansible)

Цель — показать практическое понимание DevOps-подхода в условиях, приближенных к production.

## Архитектура
Компоненты системы:

- Frontend — пользовательский интерфейс
- Backend — REST API
- PostgreSQL — база данных
- Nginx — reverse proxy
- Prometheus — сбор метрик
- Grafana — визуализация метрик

## Быстрый старт (локально)

### Требования
- Docker ≥ 24
- Docker Compose ≥ 2
- Git

1. Клонирование проекта
```sh
git clone https://github.com/ReDaX7355/DevOps-pet-project.git
cd DevOps-pet-project
```

2. Настройка переменных окружения
```sh
cp .env.example .env
```

3. Запуск проекта

Сначала запускаем веб приложение
```sh
docker compose -f docker-compose.dev.yml up -d --build
```
Затем мониторинг
```sh
docker compose -f ./monitoring/docker-compose.yml up -d
```

После запуска сервисы будут доступны:
| Сервис | Адрес |
|--|--|
| Frontend | http://localhost:80 |
| Backend API | http://localhost:80/api/ |
| Grafana | http://localhost:3000 |
| Prometheus | http://localhost:9090 |

## CI/CD (GitHub Actions)

В GitHub репозитории были созданы пайплайны, для тестирования приложения, создания образов (Frontend и Backend) и деплоя на сервере.

### Описание пайплайнов
1. `docker-build.yml` - запускается при push в dev, здесь прогоняются тесты, создаются образы в GHCR.
2. `main.yml` - при push в main, создает итоговые образы, добавляя в их имя короткий "sha" коммита.
3. `release.yml` - привязан к git tags и создает образы с наименованиями текущего тега, далее деплоит их на указанный сервер (работает только с удаленным сервером).

Требуемые SECRETS для dev:
- POSTGRES_DB
- POSTGRES_USER
- POSTGRES_PASSWORD
- DATABASE_URL
- PORT_BACKEND

Для prod:
- GITHUB_TOKEN (отдельный пароль от GitHub, создается в настройках)
- SERVER_HOST
- SSH_PRIVATE_KEY
- SERVER_USER

## Мониторинг и логирование
Была создана конфигурация для мониторинга сервера с приложением.

### Стек мониторинга
- Prometheus - основное хранилище метрик
- Promtail - чтение и сбор логов системы
- Loki - хранение системных логов и их отображение
- Grafana - вывод метрик в графики и дашборды
- cAdvisor и node-exporter - cбор статистики docker контейнеров и ресурсов системы соответственно

### Метрики (Prometheus + Grafana)
В Grafana по умолчанию есть два готовых дашборда, для отслеживания состояния сервера и Docker контейнеров.

Отслеживаются:
- загрузка CPU / RAM контейнеров
- состояние сервисов
- HTTP-запросы
- uptime сервисов и др.

В каталоге "monitoring" находятся готовые стартовые конфиги для всех сервисов.

### Логи (Loki + Promtail)
- централизованный сбор логов
- контейнерные логи

### Алерты
В Prometheus были настроены базовые алерты и установлен alertmanager для сбора и отправки оповещений.
Была протестирована отправка оповещений по почте через SMTP Yandex.

В конфиге monitoring/alertmanager/alertmanager.yml можно задать настройки отправки оповещений.

``` yaml
global:
  resolve_timeout: 5m
  smtp_smarthost: 'mail.example.com:587' # SMTP сервер
  smtp_from: 'mail@example.com' # почта - от кого
  smtp_auth_username: 'mail@example.com' # имя пользователядля доступа к почтовому серверу
  smtp_auth_password: 'example_pass' # не пароль от почты, а пароль приложения для доступа
  smtp_require_tls: true
...
receivers:
  ...
    email_configs:
    - to: 'mail@example.com' # куда отправлять уведомления
      send_resolved: true
  # Ниже под каждым именем, такжже можно настроить отправку уведомлений
  - name: page
  - name: warning
  - name: critical
```

## Создание облачной инфраструктуры (Terraform)
С помощью Terraform для веб-приложения была создана конфигурация для автоматического развертывания облачной инфраструктуры на основе провайдера Selectel. 
Она имитирует production-сценарий, где создаются 2 сервера в облаке: один для самого приложения, другой для мониторинга.

### Требования
- Terraform 1.15+
- Аккаунт Selectel с пополненным балансом
- SSH ключ, откуда будет запускаться конфигурация, загруженный в ЛК Selectel 

### Структура проекта

```
./terraform/
  - network.tf # Создание сетевой инфраструктуры (роутер, внутренняя сеть, открытие необходимых портов)
  - providers.tf # Настройка провайдера Selectel
  - servers.tf # Создание самих серверов и связка с внешним и внутренним IP
  - terraform.tfvars.example # Описание переменных необходимых для работы конфигурации
  - variables.tf # Создание переменных для использования в конфигурации
  - outputs.tf # Вывод IP-адресов серверов и строк для подключения по SSH, создание конфига inventory.yml для Ansible

```
В файле `outputs.tf` создана инструкция для создания файла конфига `ansible/inventory.yml` для Ansible, с заранее указанными IP адресами серверов.
Также в конфигурации (`/.terraformrc`) было настроено зеркало, для установки модулей провайдера, т.к. официальное RHCP не работает.

Для работы всей конфигурации необходимо создать файл `terraform.tfvars` с указанием необходимых переменных. В файле `terraform/terraform.tfvars.example` описано, какие переменные нужны.

## Настройка серверов для приложения и мониторинга (Ansible)
С помощью Ansible была создана конфигурация, для настройки окружения и деплоя приложения и мониторинга на отдельные серверы. Она используется при первом развертывании на удаленных серверах.

### Описание конфигурации
В каталоге `ansible/` были созданы 3 роли для настройки:
- docker - установка Docker и зависимостей
- app - развертывание приложения на сервере
- monitoring - развертывание мониторинга

Cоздан конфиг `ansible.cfg` для правильной работы Ansible.
Конфиг `inventory.yml` генерируется Terraform, там сразу указаны все настройки для подключения к серверам.

### Требования
- Ansible 2.12+
- SSH доступ к серверам
- GitHub Access Token для pull образов из GHCR

### Полный деплой с нуля
```bash
# 1. Клонирование проекта
git clone https://github.com/ReDaX7355/DevOps-pet-project.git
cd DevOps-pet-project

# 2. Создать инфраструктуру
cd terraform && terraform apply

# 3. Создать токен доступа в GHCR для того, чтобы Ansible мог скачать образы "frontend" и "backend".

# 4. Создать или скопировать в ansible/roles/app/files/ файл переменных .env, где указаны настройки для подключения к БД Postgres.
# В .env.example указаны все необходимые настройки по умолчанию.

# 5. Настроить серверы + задеплоить приложение
# Запустить плейбук Ansible. Необходимо указать переменные, для корректного подключения к GHCR: ghcr_username='логин в Github', ghcr_password='токен доступа из Github'
cd ../ansible && ansible-playbook playbook.yml \
-e "ghcr_username=*******" \
-e "ghcr_password=*************************"
```

### Тестирование
Создание инфраструктуры и окружения тестировалось на реальных облачных серверах Selectel.
Создаются 2 облачных сервера с помощью terraform, далее разворачивается все необходимое с помощью Ansible. 

Структура:
- Сервер 1: Frontend + Backend + DB + службы для мониторинга
- Сервер 2: Prometheus + Grafana + Loki (+ доп. модули)
